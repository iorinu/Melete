# 運動記録仕上げ 仕様案

状態: 対象範囲と4点の仕様は承認済み。UI配置および実装詳細は未確定で、実装済み仕様ではない。
基準: 現行コードと `docs/design-doc.md`（ユーザー確認待ちの設計案）
作成日: 2026-11-16

## 1. 目的・適用範囲

既存の種目・運動記録機能を土台に、項目定義の管理、保存済みセット／種目別記録の部分削除、永続化と失敗時の保護を仕上げる。対象はローカルのSwiftData運動記録であり、現行コードに存在しない将来機能を現行仕様として扱わない。

ユーザーが承認した決定:

- 項目を追加し、入力欄から外す／復帰する。項目名・単位・入力形式（整数／小数）・必須／任意を変更できるようにする。
- 全項目を入力欄から外すことはできるが、有効な項目がない状態ではセットを追加できない。
- 既存Workoutに新しいセットを追加するときは、その時点で有効な項目定義を使う。
- 新規項目定義の重複・空欄の扱いは、現行の作成ルールに従う。
- 保存済みセットまたは種目別記録を個別に削除できる。
- 保存済み削除の確認時に影響範囲を明示し、Undoは設けない。最後のセットを削除して空になる種目別記録、または最後の種目別記録を削除して空になる親の運動記録は、削除対象と一緒に削除する。
- 既存セットは記録当時の入力条件を維持し、変更後の条件は新しいセットにだけ適用する。
- 項目名／単位変更の前後は、将来のグラフと自己ベストで別に扱う。

本書で未確定とした事項は、実装前に確認する。承認済み事項と混同して確定仕様を広げない。

## 2. 現行実装と未検証事項

### 2.1 コードで確認できる現行動作

- `Melete/Models.swift` のSwiftDataスキーマは `MeleteSchemaV1`。モデルは `Exercise`、`MetricDefinition`、`Workout`、`ExerciseRecord`、`SetRecord`、`MetricValue`。
- `MetricDefinition` は名称・単位・整数／小数・必須／任意・有効状態・順序を持つ。`ExerciseForm` は作成時の項目複数追加、項目名重複の拒否、最低1項目を実装している。種目一覧では項目の編集・外す／復帰はできず、種目名編集と種目のアーカイブ／復帰がある。
- 保存時の `MetricValue` は項目IDに加え、名称・単位・入力形式・必須条件のスナップショットを保持する。過去セットの編集フォームはこのスナップショットを使い、現行定義を直接参照して再解釈しない。
- 新規Workoutへのセット値は有効な項目定義を使う。既存Workoutへのセット追加は現在の有効項目をdraft化し、保存時にも定義の一致を確認する。定義変更があれば追加を拒否する。現在の有効項目が0件の場合も追加を拒否する。
- 初回のWorkout入力ではdraft上でセット複製・セット削除（最後の1セットは削除不可）・種目除去ができる。永続化済みWorkoutの編集では値・日付編集とセット追加はできるが、保存済みセット／種目別記録の削除はできない。
- Workout全体の削除には影響を示す確認ダイアログがある。`WorkoutDeletion` は削除・保存失敗時rollbackを行う。
- 数値入力は0以上、整数または小数第3位まで。任意項目の空欄はnil、0とは区別される。値編集・セット追加は保存前検証、保存失敗時の対象Workout変更の復元と追加セットの取り消しを実装している。
- `MeleteApp` は `VersionedSchema` のV1を使う。UIテスト専用ストアの引数・所有者・権限・マーカー等を検証し、起動エラー時に実データへfallbackしない。

### 2.2 現時点で未実装または未検証

- 項目定義の編集、入力欄から外す／復帰、永続化済みセット／種目別記録の部分削除。
- 項目のrevision履歴。現在は `MetricValue` にスナップショットがあるだけで、安定IDに対する revision ID／有効期間やrevision遷移を保持しない。
- この変更群に対する旧ストアからのschema移行設計、実際の移行試験、移行失敗時のデータ保護。
- 新しい削除操作におけるSwiftData保存失敗時の具体的な復元境界・未保存変更の保持。
- 名称／単位変更前後のグラフ・自己ベスト表示（分析機能自体が未実装）。

上記のSwiftDataの挙動や移行可否は資料から推定して確定せず、実装時に調査・テストする。

## 3. 機能要件と受入条件

### FR-WR-01 項目の追加

種目に数値項目を追加できる。項目は名称、単位、入力形式、必須／任意、表示順、入力欄での有効状態を持つ。追加操作で既存保存値を作り替えない。

**受入条件**

- 有効な項目追加後、新しいWorkoutおよび既存Workoutに後から追加するセットで新項目を入力・保存できる。
- 既存の保存済みセットには追加前の項目値を後付けせず、当時の項目名・単位・入力条件・値を維持する。
- 既存Workoutへの新規セットは、そのセットを追加するときに有効な項目定義を使う。フォームを開いた後に定義が変わった場合は古いdraftを黙って保存せず、更新を促す。
- 有効な項目が0件の場合、セットを追加できない。

### FR-WR-02 項目の編集と入力欄の切替

項目名、単位、整数／小数、必須／任意を編集し、使用しない項目は入力欄から外し、後から復帰できる。

**受入条件**

- 外した項目は新規セットの入力欄・新規値生成から除外され、過去セットの履歴表示・値編集では記録当時のスナップショットで参照できる。
- 復帰後に作るセットは、復帰時点で有効な定義を使う。過去の項目値を上書き・再ラベルしない。
- 既存セットは名称・単位・数値形式・必須条件の変更後も記録当時の入力条件を維持する。変更後の条件は新規セットにのみ適用する。
- 名称または単位が変わる場合、将来のグラフ・自己ベストで変更前後を別系列・別集計単位として扱い、値を混ぜない。自動単位換算をしない。
- 新規項目定義では現行の作成ルールを適用する。現行フォームは同一種目内の項目名重複を大文字小文字を無視して拒否し、名称・単位を必須にしている。編集時の正規化など、現行ルールを超える詳細は未確定。

### FR-WR-03 保存済みセットの削除

Workout編集画面から特定セットを削除できる。確認画面には運動日、種目、セット番号、削除される値を示す。

**受入条件**

- キャンセルで永続データに変更がない。
- 確認後は対象セットとその項目値だけが削除され、同じ種目の他セット、他の種目、他Workoutは維持される。
- 対象が種目別記録の最後のセットの場合、そのセット削除と同時に空になる種目別記録も削除することを確認画面で明示する。
- 対象Workoutの最後の種目別記録もなくなる場合、空になる親Workoutも一緒に削除されることを確認画面で明示する。
- 保存失敗時は削除前の永続状態を保ち、成功表示を出さず、利用者にエラーと再試行手段を示す。

### FR-WR-04 保存済み種目別記録の削除

Workout編集画面から特定の種目別記録を削除できる。確認画面には日付、種目名、セット数、削除される値と、親Workoutも削除されるかを示す。

**受入条件**

- キャンセルで一切の永続変更がない。
- 確認後、対象の種目別記録・全セット・値を削除し、同じWorkoutの他種目と別Workoutのデータは保つ。
- それがWorkoutの最後の種目別記録なら、空のWorkoutも同じ操作で削除する旨を確認画面に示し、確認後にまとめて削除する。
- 最後のセット削除で親子が連鎖して消えるケースと、他種目が残るケースを分けて検証する。

### FR-WR-05 永続化・失敗時の整合性

削除および項目定義変更は、対象データに限定して永続化する。保存失敗を成功として扱わず、無関係な未保存変更を破棄しない。

**受入条件**

- 専用の一時SwiftDataストアに保存後、コンテナを開き直して変更・削除結果が正しく復元される。
- 故意に保存を失敗させ、対象の部分削除／定義変更が中途半端に残らず、再試行可能であることを検証する。
- 対象外モデルに存在する未保存変更が、対象操作の失敗処理で意図せずrollback／初期化されない。SwiftDataコンテキストのsave/rollbackの実際の境界をテストで確認する。
- 一つの確認済み削除に伴うセット、種目別記録、親Workoutの変更は一貫した結果となる。部分削除を成功として表示しない。

### NFR-WR-01 旧データ保護と移行

- 現在の `MetricValue` スナップショットと、将来の安定した項目ID／revision識別を混同しない。どの履歴を移行時にどう合成するかは調査で決め、推測で既存レコードのrevisionを断定しない。
- 既存V1モデルに対する移行方式（自動移行で可能か、`SchemaMigrationPlan` 等が必要か）をApple資料と実装で調査し、選択根拠を記録する。
- 旧ストアの合成fixtureを用意する。複数項目、名称・単位・入力条件が異なるスナップショット、nilと0、複数Workout／record／set、アーカイブ状態、順序、作成日時を含め、移行後に保持されることを検証する。
- 移行失敗fixtureも扱い、起動エラーを表示し、データを削除・初期化せず通常ストアへfallbackしない。実データで移行試験をしない。

### NFR-WR-02 UIテスト隔離

UIテストは既存の隔離条件を必須とし、安全条件を緩和しない。

- テスト起動引数 `--melete-ui-test-root` と `--melete-ui-test-store`、所有者・アクセス権・パス／symlink検査・root/storeマーカーを満たす専用一時ディレクトリだけを使う。
- アプリ画面の「隔離ストア使用中」表示とストアマーカーの両方を、起動時および再起動後に確認する。いずれかが欠ける／不一致ならUI操作・保存を中断する。
- 不正・欠落した専用ストア指定で通常ストアへfallbackしない。UIテストで `CODE_SIGNING_ALLOWED=NO` を付けない。
- テストfixture、ログ、成果物に実記録・個人情報・認証情報を含めない。

## 4. 要確認事項・提案（未確定）

次の扱いは未確定であり、必要に応じて実装前に確認する。冒頭で承認済みとした仕様はここで再検討事項には含めない。

1. **最後の有効項目**: 全項目を入力欄から外すこと、および有効項目がないときセットを追加できないことは承認済み。項目がない場合の案内方法と、アーカイブと項目無効化のUI上の区別は未確定。
2. **入力不可の項目**: 形式・必須条件を変えた後、既存値編集はスナップショット条件で受け付け、新規セットは変更後条件で検証する方針を明記する。アーカイブ種目での履歴編集の可否は現行コードでは値編集可能・セット追加不可。変更対象とするか確認する。
3. **項目重複**: 新規定義の重複・空欄は現行作成ルールに従うことが承認済み。編集時の大文字小文字・空白正規化ルールと、過去スナップショットで重複名になる場合の表示は未確定。
4. **削除確認UI**: 削除時に影響範囲を明示しUndoを設けないことは承認済み。セット／種目別記録の削除ボタン配置、確認文言、影響値の全表示／要約表示は未確定。
5. **並行変更**: 削除確認中に対象が別操作で変わった／消えたときは最新状態を再表示し、古い確認のまま削除しない案。現在の単一ユーザーUIで競合が発生する条件と再確認方法を要確認。
6. **失敗時の保護**: 操作関数が対象モデルだけ復元する方式と、ModelContext rollbackの巻き込み範囲を比較検証する。別の未保存変更を保護できると確認前にrollbackを広範囲に使わない。
7. **項目履歴モデル**: 名称／単位の更新でrevisionを作り、整数／小数・必須／任意の改定も新規セットの条件として識別する案。永続化方式・旧値からrevisionを復元する規則・有効期間・revision IDの整合制約を移行調査後に決める。
8. **旧セットへの新項目**: 新項目追加後に既存Workoutへセットを追加する場合、その時点で有効な定義を使うことは承認済み。一方でそのセットの項目群は既存セットと異なる。表示順・履歴の欠落表示・集計対象の扱いは未確定。

## 6. 実装段階案

1. **仕様・画面確認**: 未確定事項のうち実装に必要なものを確認する。項目編集／削除確認の具体的な画面案や表示文言は未確定。
2. **移行調査とfixture**: V1からの変更案を確定する前にSwiftData移行の制約を調査。現行V1の合成fixtureをテスト専用ストアに作り、正常・失敗移行の期待値を定める。実データでは試さない。
3. **項目定義編集**: 追加・編集・無効化／復帰と、新規セットへの適用を実装。既存値のスナップショットを維持し、revision識別が必要な変更は承認済み移行後に行う。
4. **部分削除**: セット削除、空recordの連鎖削除、種目別record削除、空Workoutの連鎖削除を確認付きで実装。対象限定の失敗復元・未保存変更保護を検証する。
5. **永続化・移行統合**: 旧ストア正常／失敗fixture、再起動後の値・定義・日時・関連データを照合する。移行不能時に初期化しないことを確認する。
6. **UI回帰・仕上げ**: 隔離ストアを使うUIテストで操作、キャンセル、確定、失敗表示、再起動後状態を確認する。既存のウィンドウスモークとWorkoutフローも実施する。

各段階は小さく独立した変更・コミット単位に分ける。未確定事項を確認しながら実装し、各段階の受入条件とテストが通った範囲を明示して進める。今回の機能について、機能単位のコミットまでユーザーから依頼されている。

## 7. テスト実行・UIテストの既知事項

本仕様案の策定時にUIテストを再実行していない。既知の経緯として、起動時のウィンドウおよび隔離ストア表示を検出できず、安全停止する事象が再発している。ユーザーは根本原因の調査より機能開発を先行することを選択した。

実装後は `AGENTS.md` のコマンドを使う。少なくとも以下を候補とする。

```sh
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer xcodebuild -project Melete.xcodeproj -scheme Melete test
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer xcodebuild -project Melete.xcodeproj -scheme Melete-WindowProbe -only-testing:MeleteUITests/WindowProbeSmokeUITests test
```

既存UIテストはテストごとに所有者限定・権限0700の一時root/store、root/storeマーカーを作成し、起動後にアプリ内の「隔離ストア使用中」とマーカーを確認してから操作する。Workoutフローでは再起動後にも確認する。検証に失敗すれば `continueAfterFailure = false` と明示的なreturnで操作を中断する。この条件を削除・簡略化しない。

この仕様策定では診断用 `.xcresult` を開かず、再実行もしていない。
