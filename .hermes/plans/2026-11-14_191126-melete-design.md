# Melete 筋トレ記録アプリ 設計計画

> この文書は設計作業の計画であり、実装の指示や完成済みの仕様ではない。

**目的:** Mac向けの筋トレ記録アプリについて、会話で確定した要件をもとに実装可能な設計を作成する。

**構成案:** SwiftとmacOSネイティブUIを使い、記録・目標をMac内に保存する。通常の記録操作とAI連携を分離し、Codexを使う場合もデータの変更はアプリの確認画面を経由させる。実装技術や保存方式は調査・設計段階で決定する。

**技術候補:** Swift、SwiftUI、macOS通知、ローカル永続化、Codex App Server。採用・対応バージョンは未確定。

## 確認済みの要求

- 当面はMacのみ。iPhone対応と同期は初期版の対象外。
- 筋トレ後にまとめて記録。1種目のセットごとに重量・回数が異なってよい。同一内容の複数セットも一括入力できるようにする。
- 自重、時間ベース、有酸素運動にも対応。利用者が種目だけでなく、数値の記録項目と単位の組み合わせを作れる。種目は初期状態では空。AIは未登録種目の作成を提案でき、記録とともに確認後登録する。
- サイドバーはホーム、記録、分析、目標、種目、設定で構成する。
- 期限付きの種目別達成目標、体重記録・体重目標を初期版に含める。達成済み・期限切れの目標は履歴として残す。頻度・継続目標の詳細は設計案として整理する。
- 初期設定で目的（ダイエット・筋力アップ・健康維持）を複数選択可能とし、後から変更できる。目的・目標の設定はスキップ可能。目的変更で過去の記録や目標を削除しない。
- 初期版に種目別の重量・回数推移、体重の推移、運動カレンダー、種目ごとの自己ベストを含める。自己ベストは選択項目の最大値とし、条件付きの最短時間などは対象外。
- 最初の運動記録前には未記録通知を送らない。体重だけの記録は運動に含めない。
- 当初は本人向けだが、将来的にOSSとして公開・配布可能な構成とする。利用者が自身でCodex CLIをインストール・ログインする方式を第一候補とする。
- AI会話から運動・体重記録および目標の追加・修正・削除ができる。いずれも変更内容と対象を表示し、毎回利用者の確認後に実行する。
- ホームに直近のトレーニング、目標、AI会話をまとめる。おすすめメニューはボタン押下時のみ生成し、表示のみで予定として保存しない。
- ホームに常設チャットを置き、アプリ起動時にAIが目標の進捗について声をかける。自動声かけはオフにでき、トークン消費をできるだけ抑える。データ不足は遅延と区別する。会話履歴はアプリに保存しない。
- 記録と目標はMac内に保存し、AI利用時に必要な情報を送る。通常の記録・閲覧・編集はオフラインで利用する。
- 未記録期間の通知は、最初の運動記録後、初期値7日経過から次の運動記録まで毎日20時。日数・時刻を変更でき、オン・オフを切り替えられる。
- 自動声かけは同じ日で関連する記録・目標が変わらない場合は一時保存した結果を再利用する。会話全体は保存しない。
- バックアップ・復元は初期版対象外。将来追加できる保存形式・移行方法を考慮する。
- Codexを最初のAI連携対象とし、既存のChatGPT/Codexサブスクリプション利用を希望。実際に利用できる方法と条件は確認する。

## 設計作業

### 1. 残る要件を決める

- [ ] AI会話開始時の自動進捗確認について、AI利用枠消費の扱い、遅延判断の基準と通知頻度を決める。
- [ ] 目標候補の初期版での扱い、入力項目と進捗判定を確認する。目標別に「判定可能」「情報不足」を定義する。
- [ ] AIへの送信対象、送信前の表示、通常操作時の個人情報保護を決める。
- [ ] 通知時刻・オンオフ、記録のない初回、過去日付記録、アプリ終了中やMac停止中の動作を定める。
- [ ] 種目の項目の型・単位・必須条件、項目の変更・削除後の過去記録、目標からの参照を決める。
- [ ] アプリの対象macOSバージョン、配布方法、会話中のコンテキスト保持期間を確認する。

### 2. 外部仕様と実現可能性を調査する

- [ ] OpenAI公式資料で、Codex App ServerのChatGPT認証、契約・利用条件、制限、必要なCodexインストール、対応環境、料金および使用量の条件を確認する。結果にURLと確認日を付ける。
- [ ] App Serverの会話・スレッドの保存先、履歴を残さない方法、モデルに許可される操作と制御方法を公式資料で確認する。アプリ側に保存しないことと、Codex側・サービス側の保持を区別する。
- [ ] 不確実な点は実現済みと扱わず、実装前にユーザーと確認する。個人の認証ファイルの内容は読まない。
- [ ] macOSのローカル通知について、アプリが起動中・終了中・Mac停止中の違い、予約数の制限、再予約や通知許可の必要性をApple公式資料で確認する。

### 3. 設計案を整理し、ユーザーの確認を得る

- [ ] ホーム、記録の一覧・追加・編集、種目設定、目標、通知設定の画面と導線をまとめる。AIの確認画面は追加・変更・削除それぞれの表示例を含める。
- [ ] トレーニング、種目、項目定義、セットと項目値、目標、通知設定の関係をMermaidで表す。数値の型、単位、既存履歴を維持する定義のバージョンやスナップショットを検討する。
- [ ] SwiftUI、ドメイン処理、ローカル保存、Codex接続、通知を責務として区切る。AIにDBや任意のファイルを直接変更させず、検証可能な提案をアプリ側で確認・保存する境界を検討する。
- [ ] 確認から保存の間のデータ変更、曖昧な対象、二重送信、削除、通信失敗、AI未設定、オフラインを扱う。
- [ ] 設計案を提示し、未決事項と採用理由を確認する。利用者の承認前に設計を確定扱いしない。

### 4. 設計完了後にdocsへまとめる

- [ ] 現行コードに依存する内容が生じた場合はOpenCodeへ反映を委譲し、Hermesが整合性を確認する。外部資料・要件整理はHermesが担当する。
- [ ] `docs/design.md` を候補として、目的・対象外・画面・データモデル・AI/通知の処理・安全境界・失敗時の扱い・受入条件・未決事項・出典を記載する。実際のファイル名は既存規約とユーザー確認に従う。
- [ ] 機能要件と受入条件にIDを付け、記録の可変項目、履歴の整合性、AIの確認必須、ネット未接続時の通常操作、通知の再設定をテスト可能な条件にする。
- [ ] Mermaid、Markdown、出典リンク、要件と受入条件の対応、ユーザーの決定事項と未確認事項を点検する。

## 検証方針

- 設計段階ではコードの実装・テスト実行・コミット・外部変更をしない。
- 将来の実装時は保存と再起動、カスタム項目の編集後も過去記録が維持されること、確認前にAI操作が保存されないこと、キャンセル・競合・再送・エラー、通知日数と日付境界、AIなしのオフライン操作をテストする。
- Codexおよび通知の実環境検証は、公式資料で確認した契約とユーザー承認に基づき実施する。実データを外部へ送る検証は別途確認する。
